You are the **App Lead** for an update to the app in `apps/<slug>/`. Arguments: $ARGUMENTS (the slug first, then the change request).

Use the same team as `/new-app`: **app-developer** (several in parallel on separate files), **code-reviewer**, **test-engineer** and **qc-inspector**. Sub-agents can't see this conversation, so every brief must be self-contained: project path, the `spec.md` path, exactly what to do, the files the agent owns, and the report format. Treat their reports as claims and check the important ones against the code. Keep small things for yourself.

## Progress and resuming

Long runs can stop when the developer's plan hits a usage limit. Keep `apps/<slug>/PROGRESS.md` as a checklist of the steps below, plus the change tasks, each marked `[ ]`, `[~]` (in progress) or `[x]`, with one line per decision or open finding. Update it after every step. **If `PROGRESS.md` already exists with an unfinished update when you start, read it and resume from the first unfinished item** instead of starting over; check the code actually matches what it says is done.

**Free only:** nothing beyond the developer's Claude subscription and their Apple and Google developer accounts. No paid services or SDKs, API keys, cloud builds or new accounts.

## Steps

1. **Understand the app.** Read `spec.md`, `REPORT.md`, `RELEASES.md` (if there is one) and `app.json`. Note the current version, and whether that version is already in a store. Never change `ios.bundleIdentifier` or `android.package` of an app that has been uploaded.
2. **Scope the change.** Decide the bump: `patch` for fixes, `minor` for new features, `major` for a redesign or a breaking change to stored data. If the change touches stored data, plan a migration so existing users keep their data. Check the request against the quality bar in `/new-app` (no thin features, no trademarks, no new data collection unless a feature needs it). Tell the developer the plan and the bump, and go ahead unless the change is big or risky, in which case ask first.
3. **Update the spec.** Add the new or changed features to `spec.md`, plus a `## Changelog` entry for the new version. Add a task list where each task owns its files, so no two parallel tasks edit the same file. You own `package.json`, `app.json` and the shared files.
4. **Build.** Give each task to an **app-developer**, several in parallel. Make the shared-file changes they ask for.
5. **Review and test.** Send the changed files to a **code-reviewer**. Ask the **test-engineer** to add tests for the change, including a migration test if stored data changed, and to run the **whole** suite and every check, so old features are checked for regressions.
6. **Fix loop.** De-duplicate the findings, check each one, and send the real ones back to an **app-developer**. Re-run the tests. Stop when there are no blockers or majors and every check passes, at most three rounds.
7. **Store material.**
   - Add or replace a `## Release notes` section in `store/listing.md`: what's new, in plain words, at most 500 characters.
   - Update the descriptions and keywords if features changed.
   - If the data the app collects changed, update the privacy answers and `store/privacy-policy.md`, run `node scripts/publish-pages.mjs <slug>`, and tell the developer the store privacy forms need updating too.
   - Run `node scripts/check-listing.mjs apps/<slug>/store/listing.md`.
8. **QC.** Send the whole app and the store files to the **qc-inspector**. Fix every fail, and re-run QC, at most two rounds.
9. **Test build on GitHub Actions.** **Before any device run (pre-flight, free and fast):** (a) `node scripts/preflight.mjs apps/<slug>` (add `--pro-preview` when the run will use `pro_preview`) prints PRE-FLIGHT PASSED. It runs every check the GitHub workflows run, here and in the same order: the Maestro flow check (every testID and text a flow uses exists; no raw `hideKeyboard`; fields that start filled in are cleared first), the lockfile, type check, unit tests, lint, Android and iOS project generation (config plugins, ProGuard rules, blocked permissions, target API level, permission texts) and the real-user walkthrough on a large phone and a 320×640 phone (the CI emulator's size: cards that run off the edge or squash a name fail here, not on a 40-minute device run). Only the native compile and the real emulator are left to GitHub; (b) the **real-user walkthrough**: `npm run walkthrough` and `npm run walkthrough -- --small --no-build` in `apps/<slug>` drive the web build with Playwright through EVERY feature the way a user would (typing, saving, checking the result where a user looks) with no console errors; the **test-engineer** writes and extends `apps/<slug>/e2e-web/walkthrough.mjs` with each feature, and the walkthrough must pass before the device run starts; (c) new Maestro flows follow the device lessons in `.claude/agent-memory/test-engineer/MEMORY.md`; (d) **every GitHub failure that pre-flight missed becomes a new pre-flight check** (in `scripts/preflight.mjs` or `check-maestro.mjs`, with a test) or a walkthrough step, plus a memory line, so the same mistake can't reach GitHub twice and runs pass on the first try over time. When only Maestro flows changed since a run, re-run just its failed job (`actions_run_trigger` `rerun_failed_jobs`) instead of a full rebuild. Run Android first and the iPhone simulator (`ios-simulator.yml`, 10× minutes) only once Android passes. When a device flow fails, read its on-screen dump and Maestro reason in the job log (`scripts/run-maestro.sh` prints them) and fix every failure of the run together before the next run. Commit and push the app, then trigger the `android.yml` workflow (GitHub tools: `actions_run_trigger`) with `app: <slug>`, `build: test`, `e2e: true`. It runs the type check and unit tests, builds an installable APK, and runs the Maestro flows on an emulator. Fix any failure through the team and run it again (at most three rounds). Give the developer the run's link: they download the APK artifact and install it on their Android phone. If the workflow can't be started from here, give them the clicks: Actions → Android build → Run workflow.
10. **Version.** Run `node scripts/bump-version.mjs apps/<slug> <patch|minor|major>`.
11. **Report.** Add a section for the new version at the top of `REPORT.md`: what changed and why, check results, reviewer and QC verdicts, open findings, and assumptions. Say whether the screenshots need retaking (they do if the UI that's shown in them changed). Finish by telling the developer to run `/release-app <slug>` to ship it.
