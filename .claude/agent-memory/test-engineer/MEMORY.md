# test-engineer memory

Lessons from earlier apps, one line each. Newest at the bottom.

- RNTL v14: render and fireEvent are async, always await them (else "overlapping act" and findBy timeouts). Jest cannot import `@/global.css` (jest.mock it or add a moduleNameMapper); mock expo-router incl. useFocusEffect/useNavigation. Helpers outside `__tests__/` (e.g. `test-support/`) so Jest does not treat them as tests.
- Device runs cost ~30 min each: before one, run `node scripts/check-maestro.mjs apps/<slug>` and the app's web walkthrough (`npm run walkthrough`, Playwright through every feature like a user) at BOTH sizes: default and `-- --small` (320×640, like the CI emulator; on 2026-11-23 it caught month tiles running off the edge and Coming up rows squashing names to "S." that only showed on the small emulator). Never trigger a device run to "see what happens". (moneyplanner, 2026-11)
- Maestro on iPhone: an accessible row reads as ONE label ("Rent, AED 9,500.00, Monthly…") — assert list rows with a regex prefix ("Rent.*"); plain text matching works on Android only. (moneyplanner, 2026-11)
- Maestro keyboards: never raw `hideKeyboard` (on iOS it taps the screen and can open another field). Text fields: Return (pressKey Enter) on iOS; number pads: the app's per-field "Done" bar (testID keyboard-done), with a scroll fallback only while the pad is up. Use the common/dismiss-*.yaml subflows. (moneyplanner, 2026-11)
- Maestro scrolling: anything under a summary (empty messages, list rows) may be below the fold on a phone — scrollUntilVisible before asserting; for buttons near the bottom use centerElement: true (the tab bar covers the last row). Fields that start filled in (day, count) need eraseText before inputText. (moneyplanner, 2026-11)
- A failed flow prints its on-screen texts/ids, Maestro's reason and Android crash logs (scripts/run-maestro.sh): read them and fix ALL failures of a run together; an empty dump plus a few-second failure usually means the app crashed. (moneyplanner, 2026-11)
- Screens pushed above the tabs (Debts, Cheques, forms) hide the tab bar: go back (Android `back`, iOS tap the header back label) before tapping a tab label like "Home". Buttons at the end of a form or sheet (e.g. a PIN pad's Continue) can be off-screen: put primary actions where they're always visible, and scroll in flows. (moneyplanner, 2026-11)
- Maestro scrollUntilVisible needs 100% of the element visible by default; near the tab bar or Android's edge-to-edge system bar that can fail although the element is on screen — use visibilityPercentage: 50 for items low on the screen. A confirm-PIN step that auto-submits has no button to tap: mark such taps optional. (moneyplanner, 2026-11)
- When a test mocks a module (e.g. `@/import/read/files`), mock ALL its exports: the developer adds exports (fileSize) and every test with a partial mock then fails inside a "never throws" catch as a generic error message. Month e2e harness: swapping to the same screen name doesn't remount, so leave and come back before re-reading totals; a share handler that reads the repo needs renderWithRepo. Web walkthrough of a Pro build: EXPO_PUBLIC_PRO_PREVIEW=1 npm run walkthrough (needs a rebuild; free-user sections must skip), Playwright `filechooser` drives expo-document-picker on web. (moneyplanner, 2026-11)
- Emulator drop-outs ("device offline", DeviceServerDiedException, failing in a few seconds at launchApp) are CI infrastructure, not the app: scripts/run-maestro.sh now waits and retries such a flow once. Don't change app code for them. (moneyplanner, 2026-11)
- A frozen system app ("Pixel Launcher isn't responding") covers the screen and fails every flow at the first step: run-maestro.sh closes system dialogs before each flow and restarts the launcher + retries once. Money Planner's own crash is never retried. (moneyplanner, 2026-11)
- A walkthrough step that fails with "expected to see X" while X is in the dump text usually means X is rendered but squashed to zero width or off-screen: look at the step's FAIL screenshot before changing the test. Later failures in the same run are often knock-on effects of the first one (skipped steps never set up the data). (moneyplanner, 2026-11)
